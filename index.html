LLM inference from scratch

An LLM inference engine I wrote in CUDA that decodes 2.7x faster than a PyTorch baseline.

Show detailsHide details
  • 150 tokens / sec
  • 2.7x faster than PyTorch
  • 790 → 4,234 concurrent sequences
  • 54% fewer cache blocks on shared prefixes
  • 2.4x throughput vs static batching
  1. Requests in. Tested on an 80k request ShareGPT trace, so the engine is measured on real conversation lengths instead of made up ones
  2. Continuous batching. A scheduler adds new requests to the running batch as soon as others finish, instead of waiting for the whole batch to drain. That gets 2.4x the throughput of static batching
  3. Paged KV cache. The KV cache is split into blocks handed out by an allocator keyed on token hashes, so prompts that share a prefix share the same blocks. That means 54% fewer cache blocks on shared prefixes
  4. CUDA decode. The decode step runs on my own CUDA code, generating 150 tokens a second, 2.7x faster than a PyTorch baseline

Key decision. Keying cache blocks on token hashes let shared prefixes reuse memory, which raised concurrent sequences from 790 to 4,234 and used 54% fewer cache blocks.

Cost aware Kubernetes scheduler

A Kubernetes scheduler for Amazon EKS that puts each pod on the cheapest node that can still meet its SLOs.

Show detailsHide details
  • 18% lower compute cost vs the default scheduler
  • 43–68% less cross-AZ network traffic
  • 13% → 72% safe Spot usage
  • 5 scoring signals
  1. Pod arrives. A new pod needs a node on an Amazon EKS cluster, and every node that can fit it is a candidate
  2. Go scoring plugin. A scheduler plugin written in Go ranks every candidate node on five signals: compute cost, network locality, latency, Spot risk and utilization
  3. Per-workload weights. Teams decide how much each signal matters for their workload by setting weights in a custom resource, so different workloads can trade cost against latency differently
  4. Placement. The pod goes to the cheapest node that still meets its SLOs, with a record of why that node won. Overall that cut compute cost 18% vs the default scheduler and cross-AZ traffic by 43–68%

Key decision. Scoring Spot risk alongside cost is what made Spot safe to use: safe Spot usage went from 13% to 72%.

Shadow testing for Kafka

Replays real Kafka traffic through the current build and the new one, then flags anything the new one does differently.

Show detailsHide details
  • 1M events end to end in ~25s on EKS + MSK
  • 79k events / sec replayed
  • 10,000 / 10,000 planted regressions caught (1% of events)
  • 0 false alarms
  • 6 / 6 escape attempts blocked
  1. Sample real traffic. Real Kafka events are sampled and replayed at 79k events a second, about 25 seconds for 1M events end to end on EKS + MSK
  2. Two builds side by side. The current build and the candidate build get the exact same events, so any difference in what they do comes from the code change
  3. Compare every side effect. Their side effects are compared event by event, and any difference fails the deploy gate. In testing it caught all 10,000 planted regressions with 0 false alarms
  4. Isolated per run. Each run gets its own locked down Kubernetes namespace. A probe pod tries 6 ways to break out and is blocked every time, while still reaching the one broker it should

Key decision. Every run is sandboxed: a probe pod tries to break out and fails all 6 escape attempts, while still reaching the one broker it should.

AI assisted Kafka recovery

When Kafka messages fail, this figures out why and gets them safely replayed.

Show detailsHide details
  • 92.9% root cause correct
  • 100% repair correct
  • 0 unsafe recommendations
  • 296K events / sec into ClickHouse (1M records)
  • 16 read-only MCP tools
  1. Dead letter queue. Failed messages from the dead letter queue are grouped into incidents and loaded into ClickHouse at 296K events a second, tested on 1M records
  2. AI investigator. A model works out why each incident happened using 16 read-only MCP tools covering Kafka, schemas, deploys and logs. It gets the root cause right 92.9% of the time
  3. Gated fix. The model can only suggest a fix. Go code checks the suggested fix, a sandbox proves it works, and a person approves it
  4. Safe replay. Only after all three checks pass does anything replay to production. So far there have been 0 unsafe recommendations

Key decision. The model can only suggest a fix, never apply one. So far that means zero unsafe recommendations.

Least privilege for AI agents

Gives an AI coding agent only the GitHub access its current task needs, and checks every call while it runs.

Show detailsHide details
  • 99.8% less access than a developer's token
  • 87.1% less access than a one-repo token
  1. Task. A developer gives the agent a task, e.g. "Fix issue #42"
  2. Model proposes a mandate. A model reads the task and drafts the access the agent needs for it: the repo, branches, files and actions the agent gets, and when they expire
  3. Code verifies it. Checked against the org's Cedar policy and the requester's GitHub permissions; state machines prove path patterns stay in bounds. The agent gets nothing until every check passes
  4. Enforced at runtime. A one-repo GitHub App token and an MCP proxy that checks every call's repo, branch, paths and destination, logging each decision. That's 99.8% less access than a developer's token

Key decision. A model proposes the permissions, but plain code has to prove they are in bounds before the agent gets anything.

Regression tests for agent attacks

Finds prompt injections that break a coding agent, cuts them down to the smallest version that still works, and turns them into CI tests.

Show detailsHide details
  • 23–33x as many hits as random search once a bug is found
  • 4 signals watched per run
  1. Sealed sandbox. Coding agents like Claude Code run in a sealed Docker sandbox, so an attack that works can't touch anything outside it
  2. Fuzz the inputs. Rewrites text such as a README to make them leak secrets or run bad commands; the search favors inputs that cause new behavior. Once a bug is found, that gets 23–33x as many hits as random search
  3. Watch four ways. Agent output, strace, file diff and network gateway, with rule-based checks instead of a model as judge, so every result is checked the same way each run
  4. Shrink and export. A Wilson interval checks that an attack reproduces reliably, delta debugging shrinks it to the smallest version that still works, and it's exported as a pytest suite and GitHub Action for CI

Key decision. Every run is checked with rules, not a model as judge, and the search favors inputs that cause new behavior.

Show detailsHide details

  • 0 memory leaks
  1. Parse. Each command line is parsed with support for pipelines, I/O redirection, subshells, command substitution and environment variable expansion
  2. Expand globs. Wildcard patterns, including ones that span multiple directory levels, are expanded into matching file names within 5% of bash's speed
  3. Execute. Commands run with signal handling and background jobs. On multi stage pipeline stress tests, it runs 20% faster than bash
  4. Clean up. Finished processes are reaped so none are left behind as zombies, and the shell has no memory leaks
